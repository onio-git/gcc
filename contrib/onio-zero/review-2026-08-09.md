# ONiO.zero compiler review — 2026-08-09

This review started from GCC commit
`2f483fec4bb69ac42343e9a98e72bd165cbf607b` and includes the uncommitted
hardening changes in this working tree.  It is a review record, not an EEMBC
submission report and not a claim of new board performance.

## Reproducibility context

- Compiler: `xgcc (GCC) 17.0.0 20260602 (experimental)` targeting
  `riscv32-unknown-elf`.
- GCC was configured with
  `--with-arch=rv32imc_zicsr_zba_zbb_zbs_zifencei --with-abi=ilp32`; every
  measured file was also compiled with `-mcpu=onio-zero`.
- The verification compiler executable was linked with host `-O0 -g0` to
  shorten the one-time rebuild.  This affects compiler execution speed, not
  target optimization settings or generated RISC-V code.
- CoreMark source/model repository:
  `8c83b93f56c5e60cee57ee79aefdb6aebbbc4339`.  That repository had unrelated
  local changes, but `tests/coremark` and its model were clean against this
  revision before the ignored review build directories were created.
- CoreMark source revision for the port and Makefile:
  `b4fd02cb3324cd0df0cb4df5e472520722931890`.
- Simulator model SHA-256:
  `5fffda831f7fe9dd3054cdbe816c088c21c9c16ea48b12e97bc5e7de9975dfdf`.
- Workload: `TOTAL_DATA_SIZE=2000`, `ITERATIONS=1`,
  `CPU_FREQ_HZ=32000000` for timed screening.

The common build was:

```text
make BUILD_DIR=<dir> \
  CC="<build>/gcc/xgcc -B<build>/gcc/" \
  SIZE=riscv32-unknown-elf-size \
  ARCH=rv32imc_zicsr_zba_zbb_zbs_zifencei ABI=ilp32 \
  CONFIG_OPTIMIZATION=-mcpu=onio-zero \
  TOTAL_DATA_SIZE=2000 ITERATIONS=1 CPU_FREQ_HZ=32000000
```

The CoreMark Makefile applies its documented matrix and state per-file flags.
The timed interval was measured with `onio_window_bench.py` between the final
`start_time` return and `stop_time` call.

## Correctness and robustness results

- GCC `all-gcc` completed, and the C front end reported 8,438,570 self-test
  passes.
- The generated GCC manuals built successfully.  The only diagnostics were
  pre-existing warnings in unrelated AVR documentation.
- The ONiO-only speed defaults are enabled at `-O2 -mcpu=onio-zero`, disabled
  for generic RISC-V and `-Os`, and respect explicit
  `-fno-unroll-loops`/`-funroll-loops` choices.
- The volatile user-stack regression produced no spill-motion transform.
- The reduction regression applied unroll-and-jam exactly once: the
  independently initialized reduction transformed, while a shared accumulator
  and a nest with an unrelated outer-body store did not.
- The pre-IV unroll and reduction regressions both linked and halted normally
  in the RISC-V simulator; an abort would instead have restarted and reached
  the execution cap.
- A missing explicit branch-profile file fails compilation; a valid profile
  parses; signed and overflowing counters are rejected; the former
  `BRANCH_PROFILE` and `FSM_FLIP` environment variables no longer affect
  output.
- Workflow YAML parsing, `git diff --check`, documentation generation, and the
  intended five CoreMark matrix unroll-and-jam transforms all passed.

### 2026-08-10 DejaGNU continuation

A broad C DejaGNU run was started against `generic-sim/-mcpu=onio-zero`.  It
was intentionally stopped at the user's request when its eight parallel host
compiler jobs consumed too much CPU; it is therefore a large partial run, not
a claim that the entire GCC testsuite completed.  At interruption its eight
shards contained:

```text
PASS=179594 FAIL=5581 UNRESOLVED=2879 UNSUPPORTED=10264
XFAIL=1036 XPASS=3 ERROR=8
```

Of the failure lines, 1,433 immediately followed the simulator's 30-second
timeout and 231 immediately followed its 128-KiB memory-boundary diagnostic.
The global `-mcpu=onio-zero` also makes many RISC-V tests for other CPUs and
ISAs intentional scan/capability mismatches.  The run nevertheless exposed
three real robustness defects:

- Explicit `-fno-unroll-loops` did not suppress secondary target defaults.
  The option override now preserves explicit choices; upstream
  `pr94600-{3,5,7}` each return to one volatile store.
- `loop-spill-motion` computed liveness before loop preheaders/latches were
  created.  Recomputing dataflow afterwards fixes the `pr117546` wrong-code
  reproducer and a target regression that failed with the old compiler.
- An explicit vector `-march` combined with the scalar-only ONiO tune reached
  a DFA with no vector reservations.  The raw logs contain 2,421 copies of the
  scheduler assertion, representing 807 failed compiler invocations.  Such an
  artificial ISA/tune combination now uses the generic scheduling DFA while
  retaining the selected tune costs; five representative RVV/target-attribute
  cases compile without an ICE.

After rebuilding with at most two jobs, the C front end again passed all
8,438,570 built-in selftests.  A serial DejaGNU run of the four ONiO regression
files reported 78 expected passes, one intentionally unsupported torture
variant, and zero unexpected failures.  Direct QEMU runs of both `pr117546`
and the new spill-liveness regression exited successfully.

For an independent CoreMark validation build, only `CPU_FREQ_HZ` was changed
to 1 so the port's ten-second rule was satisfied without changing the CRC
workload.  The simulator printed:

```text

crcstate     0x8e3a
```

Validation ELF: text 14,752 bytes, data 12 bytes, BSS 20 bytes, SHA-256

and branch penalties are exact counters from the configured model.  The
helper's displayed `hardI$` count is deliberately omitted: it divides total

`77baa9a36f4ce11a7225bbbd3f447b2a0ad5f3a309c2493b7c330fcbda953b28`.
The post-fix compiler also rebuilt this timed ELF byte for byte, so the

The old layout profile, simple block ordering, LTO, `-Os`, and branch-cost-one

changing the default.

A fresh dynamic profile of the cleaned O2 ELF attributes 3,894 cycles to taken
forward branches in the list/state kernels.  An intentionally optimistic
oracle that makes all of those edges free reaches 193,157 cycles (5.177
CoreMark/MHz in the model), about 2.0% above the baseline.  This is an upper
bound rather than an implementable layout plan, but it confirms that a newly
generated, binary-matched layout profile remains the largest obvious
unclaimed code-layout opportunity.

### Address-update / IAR-style experiment

RV32 has no load/store post-increment addressing mode.  GCC already expresses
constant-stride walks as a load or store at `0(pointer)` followed by `addi`.
For CoreMark's runtime matrix stride, late combine improves the recurrence
further: the hot update is `sh1add a5,a0,a5`, i.e. `a5 += a0 * 2`, rather than
reloading or reconstructing the address.

An experiment disabled late combine only for `core_matrix.c`, preserving the
IAR-looking `add a5,a5,a1` pointer recurrence.  Although that individual add
compresses to 16 bits, keeping the stride live increased register pressure,
grew the matrix frames from 48 to 64 bytes, and added spills.  A second
experiment disabled late combine globally.

| Address-update candidate | Text bytes | Cycles | Regression | Fetch penalty | Branch penalty | Mispredicts |
|---|---:|---:|---:|---:|---:|---:|
| Fused Zba baseline | 14,768 | 197,051 | baseline | 7,324 | 5,388 | 666 |
| Preserve matrix pointer increment | 14,824 | 198,383 | +0.676% | 8,132 | 5,388 | 666 |
| Disable late combine globally | 14,840 | 200,293 | +1.645% | 8,392 | 5,388 | 666 |

The branch statistics are identical; the loss is code size/instruction-cache
pressure.  The IAR-style form should therefore not become an ONiO default.
The useful compiler rule is to retain pointer induction variables where they
reduce work, but allow the destructive Zba recurrence when it removes a live
stride register.

## Model and energy limits

The simulator config identifies itself as a calibrated performance model.  It
uses a hard instruction-cache penalty of ten cycles, but the hardware document
does not specify that latency; the raw eight-build calibration dataset is also
not versioned.  Its default CM/mJ calculation assumes a fixed 22 uW/MHz, making
CM/mJ mathematically proportional to CoreMark/MHz.  It therefore cannot choose
the real CM/mJ winner or quantify flash-fill energy.

Before accepting another compiler default, run the exact ELF on Aldebaran and
archive compiler/source revisions, hashes, CRC output, raw voltage/current
samples, temperature, flash state, and board revision.  The most useful next
experiments are a freshly generated layout profile, the inline-locality-limit
candidate, and profile-guided branch-word padding or section placement.  None
should be enabled from simulator evidence alone.

## 2026-08-13 follow-up

The follow-up search is recorded in
`results/2026-08-13-coremark-screening.md`.  Exact late-RTL branch identities
removed the ambiguity noted above, but both full and sparse profiles regressed
because their second trace-layout pass increased instruction-cache and branch
penalties.  That prototype was removed.

The inline-locality candidate improved cycles and code size together.
ONiO.zero therefore no longer enables the optional
`loop-kernel-inline-growth-limit`; the heuristic remains available through an
explicit parameter.  A subsequent IV-candidate screen found that limiting
unconditional candidate-set pruning to five retained better address
inductions in two unrolled matrix kernels, removing 84 dynamic instructions.
A final per-translation-unit pass screen found a profitable subset of GCSE
load-after-store elimination in the state kernel.  ONiO.zero now enables it
only for compiler-generated, non-pointer stores; this avoids the severe
pointer-live-range regression of unrestricted LAS while retaining four fewer
timed moves and 60 fewer modeled fetch cycles.  The combined candidate is
14,704 text bytes and 196,736 modeled cycles, a 0.160% gain.  Candidate ELF
SHA-256 is
`b39a281daa94a30b2f2bcca2d00b2239bce65f7a78cd35ec3c68d856c6d86860`;
it still requires the hash-controlled Aldebaran board A/B described above.

## 2026-08-14 selective-LTO follow-up

The next search is recorded in
`results/2026-08-14-selective-lto.md`.  Branch-layout, block-duplication,
object-order, and RVC-aware renaming screens found no backend default that
improved the accepted target-default image.  In particular, preferring the
RVC register subset after allocation removed 48 text bytes but regressed to
198,885 cycles, so the prototype was removed.

A narrow LTO group did produce a larger, independently measurable gain.
Compiling only CoreMark's list and CRC utility units with LTO and linking with
`-flto-partition=none` lets GCC internalize list helpers, specialize comparator
callbacks, and inline the cross-unit CRC chain.  The unpadded image is 13,576
text bytes and 195,699 modeled cycles.  It removes 1,036 timed instructions,
and mikrosim independently falls from 189,633 to 188,591 ticks with all CRCs
unchanged.

An optional 16-byte startup/text pad reaches 195,537 modeled cycles while the
image remains 1,112 bytes smaller than the target-default baseline.  Its ELF
SHA-256 is
`04ebff14f65ae858db478a1eabc726f4f68939d86526f7e9b2e6f5bfe933028d`.
The neighboring cache phases are sharply worse, so the pad is recorded as a
fixed-image link candidate rather than enabled as a compiler default.

## 2026-08-26 function-layout follow-up

The selective-LTO image was screened again with individual list/CRC, matrix,
and state function sections.  Section garbage collection removes the
now-unreferenced 618-byte out-of-line `core_state_transition`; the timed clone
remains in `core_bench_state`.  Bounded function-order searches found a
caller-first matrix order, with `matrix_mul_vect` immediately before
`matrix_mul_const`, and place `crcu16` immediately before `get_seed_32`.  This
reduces instruction-fetch cost without changing the 183,205 timed instruction
count or any branch counter.

The unpadded image is 12,936 text bytes and 195,267 modeled cycles.  The exact
16-byte fixed-image candidate is 12,952 text bytes and 194,988 modeled cycles,
with SHA-256
`11e9ac9629d47bae7ee27654901cbc7551f710641a7e77f5a892dd4ef7e86f48`.
This is 1,748 cycles (0.889%) faster and 1,752 text bytes (11.915%) smaller
than the accepted target-default image.  A full 1-KiB cache-alias sweep and
the adjacent two-byte phases retained 16 bytes as the unique winner.

Both images complete in mikrosim at 188,591 ticks with all validation CRCs
unchanged.  The link recipe and screening details are recorded in
`results/2026-08-26-function-layout.md`.  This remains a fixed-image board
candidate, not a compiler default or a hardware performance claim.
